How HTTPS and TLS Work: The Padlock, Explained

What happens in a TLS handshake, how certificates and certificate authorities create trust, TLS 1.3 improvements and common HTTPS errors.

Video: Transport Layer Security (TLS) — Computerphile. Embedded from YouTube in privacy-enhanced mode; all rights belong to the creator.

The padlock in your browser means your connection uses HTTPS — HTTP carried inside TLS (Transport Layer Security). TLS gives three guarantees: confidentiality (eavesdroppers can't read the traffic), integrity (nobody can alter it in transit) and authentication (you're talking to the real owner of the domain). It does not mean the site itself is trustworthy — phishing sites get certificates too.

The handshake in TLS 1.3

  1. ClientHello. Your browser sends supported cipher suites and a key share for an ephemeral Diffie-Hellman exchange.
  2. ServerHello. The server picks parameters and sends its own key share. Both sides can now derive shared session keys — without ever sending them over the wire.
  3. Certificate and proof. The server sends its certificate chain and signs the handshake with its private key, proving it controls the certificate.
  4. Finished. Both sides confirm the handshake wasn't tampered with, then encrypted application data flows.

TLS 1.3 (RFC 8446) completes this in one round trip, removes obsolete algorithms, and makes forward secrecy mandatory: even if the server's private key leaks later, past sessions stay secret.

Certificates and the chain of trust

A certificate binds a domain name to a public key, signed by a Certificate Authority (CA). Your operating system or browser ships with a list of trusted root CAs; the server presents its own certificate plus intermediate certificates linking back to one of those roots. Free, automated CAs such as Let's Encrypt made HTTPS the default across the web. You can restrict which CAs may issue for your domain with a CAA record — check it with our DNS lookup.

Common errors and what they mean

ErrorLikely cause
Certificate expiredRenewal failed — automate it
Name mismatchCertificate doesn't cover this hostname (e.g. missing www)
Untrusted issuerSelf-signed cert or missing intermediate
Mixed contentHTTPS page loading HTTP scripts or images
Clock errorsDevice date/time is wrong

Hardening checklist for site owners

  • Redirect all HTTP to HTTPS with a 301.
  • Enable HSTS so browsers refuse plain HTTP in future.
  • Support TLS 1.2 and 1.3 only; disable older versions.
  • Automate certificate renewal and monitor expiry.
  • Fix mixed content — browsers increasingly block it outright.
